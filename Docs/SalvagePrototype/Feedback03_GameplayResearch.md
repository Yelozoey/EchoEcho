# 搬运体验反馈与玩法改版建议

日期：2026-10-31。状态：研究与提议，尚未批准为新开发范围；现Windows包与玩法不变。

## 本次玩家反馈

用户在收到新手说明后表示：“玩完了，这也太无聊了，一件一件地搬东西”，并要求查找其他项目和扩展玩法建议。这是项目用户本人报告的体验反馈；没有采集本次用时、路线、机器或无提示完成率，不等于3–5名外部玩家验收，也不标记R5整体完成。

设计判断：当前回收物主要区别是重量和分数；道路和设备几乎没有会改变决策的状态；扫描不改变搬运选择或处理方式；多数操作时间花在往返上。已有208项回归验证工程行为，不证明玩法乐趣。下一轮应先验证具体操作和选择的价值。

## 推荐方向：设施抢修与关键物资回收

保留现有三区和Echo，将一局的主目标改为回收一个有处理过程的关键组件。先做5–8分钟候选体验，时间是设计目标，需实测。

一段示例流程（非已确认需求）：

1. 接到回收数据核心的任务，玩家携带工具和一块有限供电的便携电池。
2. Echo扫描两条路线与设备，发现一条较短但有设备故障的路，另一条可绕行。
3. 玩家决定电池用于通风处理短路，还是留给核心的数据提取设备以缩短处理时间；两种选择都应能完成主目标，实际数值待设计验证。
4. 玩家走到现场，插接电池、操作开关，并在明确反馈下解除核心固定点。需要瞄准、移动或控制工具，不能全部退化成长按E读进度条。
5. 完成主目标后，可选择直接返回，或先处理一处可恢复的设备故障以取得额外成果。回收物损坏、设备停机等后果需提前可读，不靠无预兆随机惩罚制造压力。
6. 只在最后带回关键物资；零件可考虑小容量随身携带，减少无选择的重复折返。

第一轮只验证“一种工具操作＋一项电力取舍＋Echo提供会影响选择的信息”。不同时加入自由切割、大背包拼图、复杂合成、随机大地图、敌人或多人。已有场景、UI、扫描、导航、存档和流送继续复用。

工具玩法还有一个备选：更偏物理拆卸与精细回收，以拔取、转动、牵引、装配为主。手上操作更丰富，但物理调参与第一人称工具表现的成本更高，LLM的主要作用仍是协作解释。

## Echo和LLM的职责

脚本/状态机继续负责电力、工具、计时、有效路径、实际扫描结果、任务条件和所有设备状态写入。Echo保持信息协作，不替玩家开门、接线、搬运或完成机关。

LLM候选价值：理解玩家临时的复合要求，例如“我想保留电池，绕路可以；只根据已经扫描的设备给建议”，结合有时间和来源的已知记忆，说明可行选择、代价及还缺什么信息。玩家确认当前单步行动；不增加自主执行队列。

这些基础建议也可以用脚本做，不能只因生成了台词就认定AI有价值。须对照同一任务的脚本版，评价复合要求理解、依据真实性、玩家是否因此改变有效决策和等待时间。LLM只输出受校验的JSON意图，经执行层授权；实时警报不等待模型。

当前Qwen3-0.6B语义No-Go不变，本次不重新实验，不训练/换模型/上云。新功能能否由现模型稳定完成仍未知；模型实验预算与验收必须另确认。

## 建议的验证顺序与待确认边界

先确认新玩法方向与单局规则，再拆模块：设备状态和取舍 → 工具操作 → Echo信息协作 → 短任务整合，每模块独立测试记录。先以脚本Echo验证玩法，再讨论新一轮LLM质量门禁。

首次候选试玩应记录：玩家主要时间花在哪里；能否解释两种方案的区别；是否因为Echo提供的信息改变选择；是否愿意换另一种方案再玩。先保存实际观察，不预设“新增三个功能就一定好玩”。

以下均改变已确认规则，仍属待用户选择：替换3件/12分目标、增加工具与设备交互、便携电池与随身携带、故障后果及任务失败/恢复方式。当前无实现授权，不擅自修改存档、权限或游戏资源。
